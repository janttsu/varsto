83 (and the edits in 15, 68, 75, 77.8). Wire formats are frozen in
`crates/varsto-core/src/rendezvous/proto.rs`: nobody changes a message, a
signed-byte layout, a derivation or a path without telling the other two (the
file is compiled into both the client and the server). Additions of new
optional fields are fine if they default (`#[serde(default)]`).

Common rules: the common brief (.rv-common.md) applies. Each part owns the
files listed; if you must touch a file of another part, keep it to a few
lines and say so in your report.

## Decisions taken (open questions closed)

1. **Observe = STUN.** OBSERVE is a STUN Binding Request with an optional
   attribute 0xC056 carrying the control connection's UDP token; the answer is
   XOR-MAPPED-ADDRESS. The QUIC socket's existing STUN side channel (spec 60)
   carries it with no new demux, and the server never sends unsolicited
   datagrams. **PUNCH goes over the control WebSocket**, not UDP: it needs
   authentication and a reliable answer, and a target's QUIC socket drops
   unsolicited datagrams by design.
2. **Pairing blob encrypted.** Code tag via Argon2id (19 MiB, t=2); token tag
   from the `rv=` link token; both blobs sealed (spec 83.3 justifies: a fast
   hash of 10^9 codes lets the server learn the code and MITM a relayed
   SPAKE2). This deviates from the lead's `hash("varsto-pair-3-rv", digits)`
   sketch on purpose.
3. **Outer seal on peer blobs.** The peer record envelope has the vault id
   and device id in plain text and the storage name contains the device id, so
   the parts are sealed again under `derive3(K3₀, "rendezvous-blob")`.
4. **Owner keys are not K6.** Ed25519 seeded from the K6 secret and the tag
   (unlinkable, only that device can make it); pairing offers use an
   ephemeral key.
5. **Blocking client.** `ureq` 3 for HTTP, `tungstenite` 0.29 (sync, no TLS
   features; the core's rustls + webpki-roots, as ureq) for WebSockets. Reason:
   the peer TLS transport and the pairing exchange are blocking code on
   threads; tungstenite 0.29 is the version axum 0.8 uses on the server, so
   one copy in the lock file. tokio-tungstenite would have forced an async
   bridge into the blocking TLS stack.
6. **Server: axum 0.8** (http1, json, ws, tokio; no TLS: Caddy terminates).
   It includes `proto.rs` via `#[path]` rather than depending on varsto-core,
   so the musl binary does not link quinn, image, etc.
7. **Routes work with and without `/rv`.** Base URL default
   `https://varsto.net/rv`; clients append `/info`, `/v1/...`. Lookups are
   POST so tags never appear in URLs/logs.
8. **UDP port never assumed**: always from `/info.udp`. Production announces
   port 3334 (`--udp 0.0.0.0:3334 --public-udp-addr varsto.net:3334`, the
   lead's deploy); 17893 is the self-hosting default.
9. **Relay idle = 300 s** whole-session (both directions quiet), not 60 s:
   the pairing exchange waits up to five minutes for the offering person.
10. **Writes must rise:** `ts` strictly above the slot's last `ts`, so at most
    one write per second per slot; clients use `ts = max(now, last_ts + 1)`.

Functions C implements (names are suggestions; keep them `pub` for U):

- `Engine::rendezvous_keys(&self) -> Option<VaultKeys>` = `VaultKeys::new(self.root_key(), self.vault.vault_id.as_str())` (None for member devices).
- `Engine::rendezvous_owner(&self, &Tag) -> SigningKey` = `owner_key(&self.keys.signer.to_bytes(), tag)`.
- `Engine::peer_record_parts(&self, body: &PeerBody) -> Result<Parts>`: seal
  the body with the seq the last storage publish used (`RecordWriter::seal`
  as `peer::publish` does). Seq rule (decided): keep a device-local
  `own_peer_seq` (max of every seq published anywhere); the rendezvous copy
  reuses the newest storage seq when the body did not change, otherwise
  `own_peer_seq + 1`; `peer::publish` must start at `max(highest on that
  storage, own_peer_seq) + 1` so a later storage record is never shadowed.
- `Engine::merge_rendezvous_records(&self, found: Vec<(Slot, Parts)>) -> usize`:
  accept each with the `Acceptor` (like `PeerDirectory::from_saved`), merge
  into the saved directory (`SAVED_PEERS`), write it when something changed,
  return how many entries changed; then the service rebuilds the peer table
  as after a storage read (spec 73 "Peer table").
- Service thread `p2p-rendezvous`: owns one `Control` (claims own slot and
  an open offer's slot), reconnect 5 s → 5 min doubling, ping every 25 s,
  observe every 25 s via `quic::Node` (new `Node::observe(addr, token) ->
  Option<SocketAddr>` using `proto::encode_observe` through the STUN side
  channel; `begin_probe(tx)` gate as `Node::stun` does), publishes on change
  and every `PEER_REFRESH`, fetches every `PEER_FETCH` and at start; answers
  `PunchGo{id: None}` by punching (`Node::punch`) and `RelayOffer` by opening
  a `RelayStream` and serving it with the TLS responder (generalize
  `TcpTls::serve` to any `Read + Write` stream: e.g. `serve_stream<S>`).
  Everything time-limited, logged as `p2p: rendezvous ...` lines, never an
  error surfaced to the user (spec 79). Exposes a status struct for U:
  `RendezvousStatus { url: Option<String>, state: "off"|"on"|"unreachable"|"connecting", observed: Option<SocketAddr>, last_error: Option<String>, clock_skew: Option<i64>, relayed_peers: usize }` in `ServiceStatus`/`/api/p2p` (field name `rendezvous`).
- Route order in the fetch path (`p2p.rs` / `Peers`): after QUIC punch on
  record addresses fails, ask `punch` (needs our observed address), dial QUIC
  to `PunchGo.peer` with punches; then peer relays; then `relay`:
  `RelayStream` + `tls::connect`-equivalent over the stream
  (`connect_stream<S: Read+Write>`), pooled like `TlsPool` per peer while
  alive. Path name in status: `relayed via rendezvous`.
- Pairing: `pair::v3::fetch_over<S: Read+Write>(code, keys, stream)`;
  offer side: register (`register_pair_offer`, ephemeral owner, `relay:
  true` when the control connection holds the claim) when the offer opens;
  `TagFull`/`NotOwner` on the code tag → new code (`pair::new_code()`)
  before display; withdraw on close; serve a `RelayOffer` for the pairing
  slot with the existing offer handler over the stream. Join side
  (`pair::join` order): typed → link addrs → LAN search → rendezvous
  (`find_pair_offer`; its `addrs`; a `punch` is not useful for the TCP
  pairing listener, so go straight to `relay` with a zero-claim control
  connection) → `NotFound`. New `Step::Rendezvous` for progress. The
  `Connector` trait gains `fn rendezvous(&self, code, token) -> ...` so the
  order stays testable.
- `qr::Link::Pair` gains `rendezvous: Option<Token>` (`rv=` 32 lowercase
  hex, optional, old readers ignore? NO: old readers refuse unknown
  parameters (spec 51) — accepted: old app versions cannot read new links;
  note it in spec 51 and the CHANGELOG).
- `RelayStream` read timeout: set 300 s for pairing, 30 s idle for peer
  requests (as `tls::RESPONSE_IDLE`).
- Tests: `tests/nat.rs` style integration with `varsto_rendezvous::Server::spawn_for_tests()`
  as a dev-dependency of varsto-core (add `varsto-rendezvous = { path =
  "../varsto-rendezvous" }` under `[dev-dependencies]`; no cycle: the server
  does not depend on core except as its own dev-dependency, which cargo
  allows): publish+fetch merge into the directory with no storage, a
  relayed fetch of a block between two homes, a relayed pairing, rendezvous
  down → LAN and storages still work. Lab scenarios per the common brief
  item 7 (two NAT networks via the router VM, UDP blocked → relay,
  rendezvous down).
