Benchmarks: peer to peer across Europe

One device in Paris holds the files. Devices in Amsterdam and Warsaw join the vault with an empty folder and download everything: once directly from the Paris device (peer to peer), once from an S3 bucket in Paris. Measured on 9 October 2026 on rented cloud machines.

This page reports what was measured, how, what limited it, and what was not measured. The run was stopped before every planned case was done; the gaps are listed below. The numbers belong to an alpha: they describe the code as it was on that day, including fixes made during the run. The driver is in the repository under scripts/bench/, and the summarised results are published as JSON, so every number on this page can be checked and the run repeated.

Summary

  • Large files, Paris to Amsterdam (9 ms apart): 4 GiB arrived peer to peer in 159 s (27.0 MB/s), from the bucket in 180 s (23.9 MB/s). Peer to peer was slightly faster and far steadier: its two runs differed by 2 %, the bucket's by 11 %.
  • Large files, Paris to Warsaw (33 ms apart): the bucket won, 190 s (23.4 MB/s) against 423 s (10.2 MB/s) peer to peer. The peer-to-peer path used here opens a new TCP connection for every block of about 300 KiB, so each block pays a handshake and a fresh TCP slow start; the longer the round trip, the more that costs. This is the main thing left to fix (below).
  • Many small files (10 000 files, 0.27 GiB) came from the bucket at 26 files/s to Amsterdam and 17 files/s to Warsaw: one request after another, one file at a time. The peer-to-peer runs of this set were not reached before the run was stopped.
  • Every block of the peer-to-peer runs came from the Paris device: 53 892 of 53 892 blocks in four runs, none from the bucket, whose blocks had been deleted; every file matched its SHA-256 afterwards.
  • The run found and fixed five problems, among them downloads that fetched one block at a time (now eight in flight: 4.4 times faster from the bucket to Warsaw) and a peer-to-peer server that answered one request at a time (now eight: 2.3 times faster to Amsterdam). Details and numbers.

Setup and baseline

  • Machines: three Scaleway POP2-4C-16G instances (4 vCPU AMD EPYC 7543, 16 GB RAM, 80 GB network block volume, Ubuntu 24.04): the writer in Paris (fr-par-1), readers in Amsterdam (nl-ams-1) and Warsaw (pl-waw-1). Each machine had a public IPv4 address on its own interface, so there was no NAT between them.
  • Bucket: a temporary Scaleway Object Storage bucket in Paris (fr-par), the writer's region. The readers in Amsterdam and Warsaw read it across borders.
  • Varsto: 0.0.1-alpha.8 plus the fixes listed below (branch commit 37bee19; the bucket runs used 0180ca8, which differs only in two changes that do not touch those runs, the peer-to-peer server and the file watcher of a running service). A static Linux build (musl).
  • A run: a new device joins the vault with the vault key, starts the background service, pauses it, attaches an empty folder and asks the service for one sync of that folder (POST /api/sync). The time is from that request to its answer: the file list is read, every block is fetched, checked against its hash, decrypted, checked against the chunk id, and written. Afterwards the driver compares a SHA-256 list of the folder with the writer's. Then the device is removed again.

Data sets

  • Large files: two files of 2 GiB of random (incompressible) bytes, 4 GiB in all, 13 473 blocks. A set of 4 × 2 GiB plus one 4 GiB file (12 GiB) was generated and pushed to a local disk, but downloads of it would have taken too long for the time available, so the readers used two of its files.
  • Many small files: 10 000 files in 500 directories, sizes drawn from a log-normal distribution with a median of 16 KiB, cut to 1 KiB…256 KiB, one file in twenty a copy of another; 281 MiB in all. A 50 000-file set of the same shape was pushed, not downloaded.
  • Compressible text: 128 files of 4 MiB of generated web-server log lines, 512 MiB in all; zstd stores them in 138 MiB.

What “peer to peer only” means

Varsto asks peers first and storages second, so a peer-to-peer measurement must make sure the bucket cannot help. After the writer had pushed and the bucket runs were done, every object under chunks/ was deleted from the bucket. The bucket kept what devices need to find each other and to know what exists (signed ledger, file lists, device and peer records), but no file content: a block that no peer could deliver would have left the file unavailable. Then:

  • each run's pull report counted blocks from peers and blocks in all, and the driver failed any run where the two differed;
  • the readers' traffic counters (/api/p2p/traffic) showed 4 295 519 689 bytes received from writer-paris in every peer-to-peer run, and the writer's counters showed the same number sent: the stored size of the 4 GiB set, so nothing was fetched twice;
  • the path was direct, over TCP to the writer's public address, port 17893, in every run (the service log names the route it settled on). No relay was involved; a LAN path was impossible between three countries.

To Amsterdam, nine milliseconds away, peer to peer beat the bucket by a little and was much steadier: 157.6 s and 160.6 s, against 170.6 s and 189.6 s. To Warsaw the bucket was more than twice as fast. Each block of about 300 KiB is one HTTP request on a new TCP connection: a handshake, then TCP slow start from ten packets, so a block needs several round trips however fast the link is. At 33 ms that caps eight requests in flight at about 10 MB/s, which is what was measured. The bucket's HTTPS connections are kept open between requests, so their windows stay large. The fix (reuse connections, or use the QUIC path, which keeps one connection per peer) is described below; it was not measured here.

Both readers at once from the bucket: Amsterdam got 45 MB/s and Warsaw 21 MB/s, so the bucket served 66 MB/s in total without slowing either reader down; the bucket is shared infrastructure built for many readers. Peer to peer with both readers at once was not measured; the Paris device used 40 s of CPU time to serve each 4 GiB run (one core about 25 % busy), so CPU would not have been its limit.

The reader's own work was the same for both sources: about 40 s of CPU time for 4 GiB (decrypting, two hashes per block, writing), and at most 490 MB of memory.

From the bucket a file took 40 ms to Amsterdam and 60 ms to Warsaw on average, 2.5 times the plain request time measured with rclone to Amsterdam (16 ms) and a little more than it to Warsaw (52 ms). The rest is per-file work on the reader: a new file, its data synced to disk, a rename, ledger events. Both readers at once were no slower than one alone; the bucket did not notice the second reader. The peer-to-peer runs of this set were not reached. Because the files are fetched one after another, they would be bound by round trips too: one TCP connection and one request per file.

  • Text costs about 85 s of CPU per GiB: zstd at level 12, a format constant, is slow on compressible data; it buys the 3.7 : 1 ratio every later transfer profits from.
  • Small files are not CPU-bound even on a RAM disk: 10 000 files took 50 s, of which 12 s CPU. The device's logical clock is written to disk, with two syncs, for every file pushed; on a network volume each sync waits for the storage. Not fixed yet.
  • The bucket is slowest by far: every block is a HEAD and a PUT, one after another. 10 000 files took 622 s and 4 GiB took 578 s (7.4 MB/s), single runs. Uploads are not parallel yet.

Still slow, and why

  • One TCP connection per block on the peer-to-peer TCP path. Each request opens a connection and closes it (Connection: close), so it pays a handshake and a fresh slow start. A device whose address can be reached directly is asked over TCP before QUIC; QUIC keeps one connection per peer with its window open. Either keeping TCP connections open or preferring QUIC for addresses outside the LAN should lift the Warsaw number toward what the link can carry. This is the next fix; it was not measured here.
  • Small files go one at a time. The eight-block window works within a file; a folder of single-block files still fetches one file after another. Fetching ahead across files is the fix for the 10 000-file case, from peers and from buckets alike.
  • A disk sync per file for the logical clock when pushing, as above.
  • Uploads to a bucket go one block at a time, with a HEAD before every PUT.
  • The ledger grows by about 1 KB per block: pushing the 4 GiB set wrote a 13 MB ledger batch, which every device reads when it joins (a new device took 16 s to join from Warsaw).

When peer to peer wins, and when the bucket does

Varsto uses both on purpose, and the measurements show why.

  • Peer to peer needs a peer online. The readers could fetch only because the Paris device was running. The bucket is always there: a laptop that is closed, a phone in a drawer, a device that is never online at the same time as another all still sync through it. That is why a vault always has at least one storage, and why the file lists and the ledger stay in it.
  • Near devices, peer to peer was as fast or faster, and steady. To Amsterdam it beat the bucket in both runs, with 2 % spread against the bucket's 11 %. On a LAN the round trip is a fraction of a millisecond, and no cloud is involved at all.
  • Far devices, the bucket won today, because of the per-block TCP connections described above, not because of the network: the link to Warsaw carried 738 Mbit/s in one stream.
  • Many readers at once favour the bucket unless they help each other: the bucket served two readers at 66 MB/s together without slowing either. A single home device serving many others is limited by its upload. Varsto does let readers serve each other, but that was not measured.
  • Peer to peer costs nothing per gigabyte and leaves no copy with a provider. The data goes from your device to your device; the bucket does not even need to hold the blocks for the devices to sync, only for the devices that are offline.

Cost

Scaleway's public price list (read on 9 October 2026, Paris region, before tax): Object Storage Standard Multi-AZ €0.000022 per GB-hour (about €0.016 per GB-month), requests included, ingress included, egress the first 75 GB a month free and then €0.01 per GB. Transfers between regions (Paris – Amsterdam, Paris – Warsaw) count as egress; within a region they are free.

So one reader in Amsterdam downloading the 4 GiB set from the Paris bucket costs about €0.04 once the free 75 GB are used, and a household that syncs 500 GB a month to devices outside the bucket's region pays about €4 a month in egress. Peer to peer moves the same bytes over the devices' own connections and adds nothing to the storage bill. Other providers charge more for egress or per request; the method above applies to them unchanged. The machines for this benchmark (three instances at €0.147 an hour for about four hours) cost under €2.

Limits of this benchmark

  • Incomplete: peer-to-peer runs exist for the large-file set from each reader alone; small files, text and two readers at once were measured from the bucket only. Push numbers to the local disk and to the bucket are single runs.
  • Cloud machines, not homes. Data-centre links, public addresses on the interface, no NAT, no Wi-Fi. At home the peer-to-peer path is usually QUIC through a hole-punched NAT, which these runs did not exercise; home upload speed would often be the limit.
  • Three regions of one provider, in Europe. The bucket and the machines share a provider and its backbone; other providers and longer distances will differ.
  • Network block volumes make every disk sync slow (milliseconds), which weighs on small files; a laptop's SSD syncs faster.
  • Two runs per case are few; the bucket's results varied by up to 58 % between repetitions for small files and by a factor of 2.5 for text.
  • Alpha software. Formats and defaults may still change, and so will these numbers.
