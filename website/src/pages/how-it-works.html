How Varsto works

The technology behind Varsto, one mechanism at a time: how a file becomes encrypted blocks in padded packs, which keys exist, how the signed ledger keeps track of every copy, how devices sync and find each other, and what is not done yet.

Everything here is implemented in the source-available core (crates/varsto-core) and described with exact field layouts in the storage format. It is alpha software: formats may still change, and neither the design nor the code has been audited. The threat model and the failure model say what it does and does not defend against.

Overview

Varsto has two kinds of parts, and nothing of ours in between.

  • Your devices (laptops, desktops, phones) hold the keys. They cut files into blocks, encrypt and decrypt, and run the sync in a background service.
  • Your storages hold ciphertext only: an S3-compatible bucket, any rclone remote, a NAS or network share, a local or removable disk, or a pool of disks on a shelf. Varsto needs nothing from them beyond put, get, list and delete.

Every storage holds two kinds of object: packs, which are files of fixed sizes that hold encrypted blocks of file content, and small signed records: each device's file lists (manifests), its block maps, its ledger, and the records for devices, folders and policies. Every path has exactly one writer: a device writes only under its own id, and packs are named by the hash of their bytes and never overwritten. Storages therefore need no locks, and each one doubles as a mailbox: devices that are never online at the same time still converge, as long as they share one storage. Devices can also exchange blocks directly, on the LAN or across the internet.

There is no Varsto account, server or relay. If the project stopped tomorrow, your installed devices would keep syncing through your storages.

From file to encrypted blocks

  1. Chunking. The file is cut into content-defined chunks whose size follows the file: for files under 32 MiB chunks of 64 KiB to 1 MiB, 256 KiB on average; up to 1 GiB 256 KiB to 4 MiB, 1 MiB on average; above that 1 to 16 MiB, 4 MiB on average (a rolling hash picks the cut points), so an edit in the middle changes a few chunks, not the whole file.
  2. Identity. Each chunk gets an id: a BLAKE3 keyed hash of its plaintext under the folder's dedup-hash key. The same content in the same folder has the same id on every device, which makes deduplication work offline; the key stops anyone without it from testing whether you hold a known file.
  3. Compression. The chunk is compressed with zstd when that saves at least 5 %. The level is a format constant, so every device produces the same bytes for the same chunk.
  4. Encryption. XChaCha20-Poly1305 under a chunk key and nonce derived from the folder key and the chunk id, with associated data naming the vault, the folder, the chunk and its length. Deterministic keys are safe here because each key encrypts exactly one message, and they let two devices produce byte-identical blocks without talking.
  5. Packing. Encrypted blocks are placed back to back in a pack. A pack has exactly one of a few sizes: 256 KiB, 1, 4, 16 or 64 MiB (and 256 MiB on cold storages). What is left after the last block is filled with random bytes, so nothing in the pack shows where the blocks end, and the pack has no header or index. A small edit therefore costs one 256 KiB pack; on the benchmark data the padding added 1.3 % to 1.6 % to what was stored, and compaction later merges small packs.
  6. Naming. The pack is named by the BLAKE3 hash of all its bytes. Any copy, anywhere, can be checked against its name without any key: that is how replicas, peers, fsck --verify and automatic verification check copies they cannot read.

Where each block lies inside the packs is written in a block map, one per folder and writing device, which is encrypted under the folder's metadata key. A device that holds the folder key looks a block up in the map, reads that one range of the pack, and checks the block against its own hash. A storage, or a device without the folder key, sees pack ids and size classes only: not block names, block sizes, offsets or which pack belongs to which file.

Known trade-off: deterministic (convergent) encryption inside a folder means that two people who both hold the folder key can tell whether they have an identical file. Within a shared folder that stays true for one key epoch; removing a member gives the folder a new random key, so a removed member cannot recognise anything written afterwards.

Keys

Everything starts from one random 256-bit vault key, created on the first device and never derived from anything you type. It opens the vault's bookkeeping (device and folder names, settings, the ledger of packs) and no file content. The folders' content keys are separate.

  • On each device the vault key and the device's own keys are stored in keys.enc, encrypted under a key that Argon2id derives from the device passphrase. Changing the passphrase re-wraps that file and touches nothing in storage.
  • Per device there are two key pairs, both made on the device and never shared: a signing key (Ed25519 + ML-DSA-65) that signs everything the device publishes, and a key-exchange key (X25519 + ML-KEM-768) that other devices use to send it secrets. Their public halves are in the device's record; the device id is a hash of the signing key, so nobody can publish a record under another device's id.
  • Vault-wide keys are derived from the vault key by purpose: the device registry (names, settings, participants), the ledger and the epoch records. A compromise of one derived key does not expose the others.
  • Per folder there is a random folder key. It is not derived from the vault key and is not written in any folder record. It exists only as grants: the folder key sealed to one device's key-exchange key, written by an owner of the folder. A device that holds a grant to itself holds the folder. From the folder key come the dedup-hash key, the metadata key (file lists, block maps and thumbnails) and one key per chunk. One folder key opens that folder and nothing else.
  • Recovery escrow. Every folder key is also stored once more, encrypted under a key made from the recovery words and the vault key (see the recovery kit below). Without the recovery words it cannot be opened; with them and the vault words it brings back every folder.

Adding a device. A new device gets the vault key by pairing with a device you already have, or from the vault words of the recovery kit. That gives it the bookkeeping and no folders. For each folder it publishes a request, and an owner device must approve it by hand: the approval shows the device's name and a six-word fingerprint of its two public keys, which you compare with what the new device shows. Only then does an owner write the grant. The background service never approves anything on its own. Pairing is the one shortcut: you choose the folders on the offering device, whose screen shows the same fingerprint.

Removing a device starts a new key epoch: a new random vault key, sealed to each remaining device, and a new random key for every folder the device took part in, granted to the devices that stay. New records, packs and blocks use the new keys, and a chain of encrypted epoch records lets the new vault key open everything older. The removed device finds a signed revocation the next time it reaches a storage and stops; with a wipe order it also empties its folders and keys.

Signed records

Everything a device publishes except packs has one envelope: the kind of record, the vault, the folder it concerns, the device and a sequence number, the name of the key that opens it, the hash of the encrypted body, and the hybrid signature over all of that. The body is compressed, encrypted, and padded with random bytes to a multiple of 64 KiB (1 MiB for large ones), so a storage sees record sizes only in steps. A reader accepts a record only after one set of checks that is the same for every kind: the signature verifies against the writer's key, the writer's role in that folder allows this kind of record, the body opens, and the contents pass the limits. Anything else is counted as junk and ignored, which is why a viewer or a removed device cannot write something that counts, even though it holds a key.

The ledger

The ledger is Varsto's bookkeeping. Every device keeps its own append-only log of facts about what it did, and no device ever writes into another one's log. The facts are small and concrete: "I wrote pack 5c1e to the storage I call box", "I downloaded 5c1e from box and its hash matched", "I published version 12 of this folder's file list".

Every device reads every other device's log through the storages and replays all of them into the same picture: which packs exist, where every copy is, who wrote it, who has checked it and when. Nothing in it is trusted for where it came from: each batch is signed by the device that made it, and a copy counts as verified only when a different device has checked it.

Without the ledger, a sync tool can only hope its copies exist. With it, Varsto can say how many copies of every pack there are, in which places, how recently each was checked, and which ones nobody has checked yet.

Signed, chained and sealed

Events are collected into batches, typically one per sync rather than one per file. A batch carries the device id, a sequence number (1, 2, 3, ...), the hash of the device's previous batch, a logical clock, its creation time, the newest batches of other devices it has seen, and the events. A batch is a signed record like any other:

  1. The body is compressed and encrypted with XChaCha20-Poly1305 under the ledger key, with the record's fields as associated data, and padded to a size class.
  2. The device signs the envelope, including the hash of the encrypted body, with both Ed25519 and ML-DSA-65. Signing the ciphertext hash means anyone can check the chain without the key.
  3. The signed batch is written to every storage that holds records as ledger/<device>/<sequence>, never overwritten.

A reader accepts a batch only when both signatures verify against the device's public key in the device registry and its previous-hash matches. The post-quantum signature costs about 3.3 KB, which is why events travel in batches: the ledger grows by a few kilobytes per sync, not per file.

Exchanged through your storages

Every storage is a mailbox. After a device commits a batch it uploads every batch of its own that a storage lacks; on every pull it lists the ledger on each hot storage, takes the batches it has not seen, checks them, decrypts them and keeps a local copy. Because each storage carries the whole ledger, a laptop that syncs at night and a phone that syncs in the morning see the same history without ever meeting. Nobody orders anything centrally: a logical (Lamport) clock orders changes, not the wall clock. Untrusted replicas and the people you share a folder with write ledgers too, sealed under keys that open only their part: a replica's claims name packs, not files, and a member's claims cover only the shared folder.

The view: where every pack is

Replaying all batches gives each device the same view: for every pack, its id and size class, the storages that claim a copy and which device claimed it, and which devices verified it there and when. It also knows the newest file list and block map of each device for each folder, the devices and folders that exist, and which storages are retired. Storage names are local to each device ("box" here, "primary" there), so every storage carries a random identity, and devices match each other's claims by it. Which block is in which pack is not in the ledger; it is in the folder's block map, which only holders of the folder key can read.

What it is used for

  • Uploading once. Before pushing, a device looks each block up in its block map and skips every storage that already holds it, so a file added on two devices goes up once.
  • Freeing space safely. A file becomes a placeholder only when the view shows every block on a storage that is not a transferrer, and the folder's copy rules still hold.
  • Durability policies. "At least three copies, one of them in the cloud, each verified by another device within 30 days" is evaluated from the ledger and the block maps alone, and the service raises an alert when a folder gets worse.
  • Automatic verification. The background service picks packs that other devices wrote and nobody has checked recently, downloads them, compares the hash with the name and records the result, within a daily budget. This needs no folder key, so replicas can do it too.
  • Bit-rot check. The service also re-hashes, on a rolling schedule, every copy the ledger places on this device's storages and attached disks, whoever wrote it, and the synced files on the device. It records nothing (a writer re-reading its own copy is no independent verification); damaged copies go to repair, and a damaged local file is moved aside and restored from the vault.
  • Repair. A pack that is missing or damaged on one storage is copied whole from another storage that holds it intact. If no storage has it intact, the good blocks are written into a new pack and the others are marked lost until a device that holds the file writes it again.
  • fsck. Compares the ledger with what the storages actually list: claims without a pack, packs that no block map lists, blocks with no copy anywhere.
  • Transferrer disks. A carrier disk takes only the blocks no other device holds yet, and gives the space back once both ends have them.
  • Removing a storage. Varsto plans from the view which blocks would fall below the folder's minimum, copies them elsewhere, checks again and only then records the retirement.
  • Costs. A storage's monthly cost is the pack bytes the ledger records on it times its price.
  • Removing a device. A revocation names the last batch of the removed device that counts; anything it signs later is left out of every view, and only the records those batches announced are merged.

Deleting safely

A block is deleted only when nothing refers to it, and no single device decides that alone. A device that finds a block that no current file, trash entry, version or snapshot uses writes a dead mark for it in its next block map. Nothing is deleted yet. The mark is settled once every device that can write to the folder has signed a batch acknowledging that it has seen the mark. Only then may a device delete, and only if it still finds no reference. A device that re-added the same file before it saw the mark announced its file list before it acknowledged the mark, so the collector sees the reference first and writes an undead mark instead. A pack is deleted when every block in it is collectable. A hot pack that is more than half dead is rewritten into new packs; cold storages are never rewritten and keep a pack until its minimum storage time has passed. A pack that no block map mentions is removed after seven days. The price is that cleanup waits for every writing device: one that never syncs again holds back collection in its folders until you remove it.

Forks and restored devices

Because each device numbers and chains its own batches, history cannot be rewritten quietly. Two different batches with the same device and sequence number, or a batch whose previous-hash does not match, are a fork: every device that sees one marks that device as forked, and fsck reports it. The usual cause is a device restored from an old backup or a cloned disk, which would carry on from a sequence number its newer self has already used. When a device finds batches under its own identity that it never wrote, it fences itself: it stops signing and pushing until it is enrolled again as a new device, so two diverging copies of one identity never both write history.

Rollback warning

A storage that serves an older but valid part of the ledger cannot be caught by signatures alone. Varsto uses the other devices for this. Devices publish the newest batch they hold of every device and, when they meet, exchange signed proofs of batches they have seen. If a storage keeps showing less than a device has proved to exist, and the device that wrote the batch said it uploaded it there, the warning reads: storage X may be withholding or rolled back: it shows ledger batches of D up to n, but a peer proved m. It appears after two pulls in a row, so one slow answer does not cause it, and it clears when the storage catches up. It judges only storages a device has confirmed uploading to, and a vault with one device has nothing to compare against.

Limits

  • A signature proves that a device said it stored a pack, not that the pack is still there. That is why a copy counts as verified only after another device has checked it; there is no challenge-response proof of storage yet.
  • The rollback warning needs another device that has seen the newer batch, and is not a guarantee.
  • The ledger grows with every sync. Devices write checkpoints and prune acknowledged batches, so what is stored stays bounded; the batches of a shared folder are kept, because its members cannot read the checkpoints.
  • Verification times come from device clocks: a badly wrong clock can cause false alerts, though it does not change the order of changes.
  • Storages see the number of ledger directories (your device count) and the size and timing of batches.

File lists and sync

The ledger says where packs are; manifests say what the files are. After a change a device publishes a new manifest for a folder: every path with its size, modification time, content hash, block list and a version vector (for each device, the clock of its last change), and whether this device holds all of the file's blocks. It is encrypted under the folder's metadata key and announced in the ledger. To keep this small, most manifests are a delta that lists only the paths that changed since the previous one. A full base is written first and then again after at most 1024 deltas, or earlier when the deltas have grown to about a sixteenth of the base. A device that joins reads the newest base and the deltas after it; block maps work the same way. Other devices fetch the manifests they have not seen and merge path by path:

  • a version that includes the other wins; identical content merges;
  • an edit beats a concurrent deletion, so a deletion never destroys someone's work;
  • two different concurrent edits give a deterministic winner (larger clock, then device id), and the other version is kept as name.conflict-<device>-<clock>.ext, so both devices converge without another round.

Deleted files go to a trash, never removed outright, and replaced versions go to a version history. Both are signed records of the same base and delta kind, so every device agrees on what is in them and when they expire. Backups keep read-only snapshots, each stored as a difference against a base, so that expiring one never breaks another. The background service watches your folders and syncs within seconds of a change. Selective folders show every file but keep placeholders for those you have not fetched, and fetch a file when you open it.

Peer to peer

Devices also exchange blocks directly. A device that needs a block looks up the pack and range in its block map, asks its peers first and the storages second, and spreads consecutive blocks over the peers that answer. The receiver checks the block against its own hash like a block from any storage.

  • Finding each other. Every device publishes a signed peer record in your storages with its addresses and its certificate hash. On the LAN, a multicast beacon carries a keyed tag, not the vault id, and is signed; it only suggests an address, and the handshake checks the device.
  • Crossing NATs. TLS 1.3 over TCP on the LAN and where a port is reachable, QUIC over UDP across the internet: STUN tells a device its public address, both sides punch holes, and when that fails, one of your own reachable devices relays. There is no vendor relay.
  • Who may connect. Both sides present their own certificate, and each accepts only a certificate that a signed peer record of a trusted device of the vault names (a pinned certificate). There is no plain-text connection. Every request also carries a short-lived proof tied to that one TLS connection, so it cannot be replayed elsewhere, and it uses no vault secret. A stranger gets nothing, and a removed device is dropped from the peer list.

Tested on localhost, on the maintainer's own networks and on a three-device rig across NATs. Two symmetric NATs cannot be punched and fall back to a relay, which needs one reachable device in the vault (a home server, a VPS, a forwarded port); sockets are IPv4 only.

How fast. Benchmarks measures downloads between Paris, Amsterdam and Warsaw, peer to peer against an S3 bucket, with the method, the numbers and what is still slow.

Transport and the local interface. Packs and records are ciphertext before they leave the device, so transport adds no second layer for its own sake. S3 is spoken over HTTPS with Signature Version 4, rclone remotes use rclone's own configuration, and the S3 secret is kept in an encrypted file. The desktop interface is served only on 127.0.0.1, every request carries a per-session token, the Host header is checked, and the page runs under a strict Content Security Policy.

Sharing a folder

To share a folder with another person, whose devices are not in your vault, their device first makes a request code. The code holds the device's name and its two public keys (signing and key exchange), and it can travel over any channel. Your device shows six words derived from the code. You read them to each other over a call or in person; a code swapped on its way shows other words, and you add the person only after they match.

Adding the person is two records: the folder record that lists their device as an editor or viewer (never owner) with its public keys, and a grant, which is the folder key sealed to that device's key-exchange key with both X25519 and ML-KEM-768. Only that device can open the grant, and it opens one folder. Because the person has no access to your registry, the grant also carries the folder's directory: its name, creator and participants. Your devices and theirs then write their claims for that folder in batches sealed under a key derived from the folder key, so both sides see each other's claims for that folder and nothing else. Your vault key is never shared.

Roles are enforced by every reader, not by who holds the key: a viewer holds the folder key and can read, but its records are refused everywhere. Removing a member gives the folder a new random key. Your devices and the members who stay receive it as new grants, everything written from then on is under it, and the removed member's later changes are ignored. What they already received stays readable to them; a key cannot be recalled.

Strongroom: cryptographic, not a dialog

A Strongroom folder's key is never at rest. At creation the security key makes a credential, then produces a 32-byte secret from it and a random per-folder salt (FIDO2 hmac-secret). Varsto wraps the folder key under that secret and stores only the credential id, the salt and the wrapped key. Unlocking repeats the touch and keeps the key in memory for a window (15 minutes by default), then forgets it. There is no path to the folder key without the physical key: not through the passphrase, the vault key or a stolen backup, and no grant or recovery copy of it is written. Backup security keys get their own wrap of the same folder key. Converting an existing folder gives it a new id and key, re-encrypts it and deletes the old ciphertext; re-keying a Strongroom does the same with a new key wrapped for every enrolled security key, for when a key may have been kept by someone.

Passphrases and the recovery kit

The device passphrase goes through Argon2id to unlock keys.enc; the background app can keep it in the operating system's keychain so the service unlocks itself after login. Losing a passphrase loses that device's copy of the keys, not the vault: another device, or the recovery kit, enrols a new one.

The recovery kit has two sets of 24 BIP-39 words (a miscopied word is caught by the checksum). The vault words are the vault key: with them alone a new device sees the vault's bookkeeping (device and folder names, where packs are) and no content. The recovery words open the recovery escrow of every folder key: alone they open nothing, and together with the vault words they bring back every folder. If you ask, the recovery words are also split into three Shamir shares of which any two rebuild them while one alone reveals nothing. Varsto warns you until every folder has its escrow copy. There is no account, no reset and no copy held by us: the kit is how you carry the responsibility. Print a new kit after removing a device, because the old vault words hold the old key; the recovery words do not change, so existing escrow copies stay valid.

What is not done

  • Not audited. The algorithms are standard and the libraries well-known Rust implementations, but the composition has not been reviewed by an outside cryptographer, and the storage format may still change.
  • No migration. This is storage format 3. A vault made by an older alpha build is not read: create a new vault and add your folders to it again.
  • Metadata. Storages see pack sizes in a few classes, record sizes in steps, when things are written, the number of devices and the number of packs. Cover traffic is not implemented, and padding hides sizes, not the times you write.
  • Convergent encryption inside a folder lets co-holders of the folder key confirm identical files.
  • Removing a device protects what is written afterwards, not what the device already held: existing data is not re-encrypted, shared and Strongroom folders keep their keys, and storage credentials are not rotated. Until a second factor exists, any of your devices can remove any other (in a vault with an organization, only administrators can).
  • Removing a member of a shared folder protects what is written afterwards; the storage you both reach stays writable to them until you change its access.
  • The ledger has no proof of storage, and the rollback warning only works when another device has seen the newer batches.
  • Cleanup waits. Deleting blocks and pruning old block maps and file lists wait for every device that writes or reads the folder to acknowledge; a device that never syncs again holds them back until you remove it.
  • Small pushes are padded. A tiny change writes a 256 KiB pack on every storage it goes to, until compaction merges small packs. Imports, moves and repairs still write a separate pack for each storage instead of identical packs on all of them.
  • Placement. A folder can be written to chosen storages or places, and blocks can be moved between storages (keeping only a cold copy of idle files). Files whose blocks are only on cold storage are not fetched until you move them back.
  • Strongroom protects the folder key, not a file you fetched and left on disk; the recovery kit does not cover Strongroom folders.
  • The vault key and the recovery words are secrets you have to keep. Keep the recovery kit in more than one place.
