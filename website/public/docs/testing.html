Testing

From TESTING.md in the repository, rendered 2026-11-07. These documents describe the main branch; the released version is 0.0.1-alpha.16. Sections marked 'after 0.0.1-alpha.16' are not in a release yet.

Varsto is tested in layers. The goal is that cheaper AI systems and scripts can run most tests from written instructions, while a human covers what cannot be automated (Windows, macOS, Android and iOS on real devices).

Alpha (0.0.1-alpha.16): the Rust core, the CLI, the background service with tray and web interface, and the Android, macOS and iOS (Simulator) shells exist (crates/, apps/). CI builds and tests all of them on GitHub-hosted runners; the VM levels below are prepared for what CI does not cover.

Principles

  • Machine-decidable results. Every test returns an exit code and a machine-readable result (JUnit XML plus JSON). A tester should never have to judge "did it work?" by reading prose.
  • Reproducible. Randomised and simulation tests print their seed; any failure can be replayed with the seed.
  • Disposable environments. Linux tests run in throw-away virtual machines or containers that can be started, broken and destroyed without limit.
  • Synthetic data only. Never use real user data or real credentials. Test data is generated by scripts.
  • Safe for AI agents. Agents follow docs/testing/ai-runbook.md. They run tests and write reports; they do not change production code unless explicitly asked.

Test levels

  1. Unit and property tests (Rust core).
  2. Integration tests against real storage back ends: MinIO (S3), an SFTP server, a local folder, rclone remotes, an S3 server emulating storage classes and restore delays (cold storage).
  3. Deterministic simulation of the sync and bookkeeping protocol with fault injection (network partition, crashes, clock skew, partial writes).
  4. Multi-device scenarios in virtual networks (LAN-only sync without internet, NAT types, packet loss).
  5. Removable-disk scenarios (hot-plugged virtual disks, unplug during write, corruption, full disk, cloned disk).
  6. Upgrade and migration tests, long soak tests, performance tests (very large files, millions of small files).
  7. CLI contract tests (JSON schema, exit codes).
  8. Security tests: fuzzing, dependency audit and licence checks, secret scanning, reproducible-build comparison.
  9. Mobile tests: see docs/testing/mobile.md. Devices: docs/testing/devices.md.
  10. Manual tests on Windows, macOS, Android and iOS: see docs/testing/manual.

The distribution list in tests/matrix.yaml is also a plan: only debian-stable on x86_64 has an image in scripts/test, and the lab uses Debian 13.

The rendezvous service (docs/rendezvous.md) is tested in three places. crates/varsto-rendezvous/tests runs the server in process (Server::spawn_for_tests) against the core client. The core's integration tests (next to tests/nat.rs) run two engines in one process against that server: record publish, fetch and merge, observed address, punch coordination, relayed fetch, relayed pairing, and "service unreachable: LAN and storages still work". The interface side is covered by the translation test (interface_translations_cover_the_page, every new string in fi and sv), the API shape test for /api/p2p (rendezvous and the rendezvous_on / rendezvous_url settings) and node --check crates/varsto-cli/ui/app.js. The screenshot fixtures (scripts/screenshots/example_data.py) show the rendezvous card and a peer relayed via rendezvous with the invented address https://rv.example.org. Lab scenarios run the service on the lab host with the two devices behind two NAT networks; any scenario that must work without it runs with the service off.

Running tests (Linux)

Rust (levels 1 and 2, no VM needed)

cargo test --workspace                 # unit tests, two-device sync scenarios, CLI smoke test
cargo clippy --workspace --all-targets
cargo fmt --all --check

The integration tests in crates/varsto-core/tests/ simulate two devices that are never online together, a concurrent edit, and a device restored from an old backup (which must be fenced). The CLI test in crates/varsto-cli/tests/ runs the built binary end to end with --json.

A test or a throwaway service that runs varsto service run sets VARSTO_NO_PORT_MAPPING=1 (as the CLI tests do), so that it never asks the router of the network it runs in to open a port (spec section 52). Router port mapping is tested against fake PCP, NAT-PMP and UPnP gateways on the loopback interface (p2p::portmap::tests); free-space limits with the fake provider pool::set_fake_space.

Virtual machines (levels 3 and up)

scripts/test/provision-vm.sh <distro>      # create a disposable VM, prints its name
scripts/test/run-suite.sh <suite> <vm>     # run a suite in that VM
scripts/test/collect-logs.sh <vm>          # fetch logs and results
scripts/test/destroy-vm.sh <vm>            # always destroy the VM afterwards

Every script accepts --dry-run, which prints the commands without executing them.

These scripts have only the smoke suite and the debian-stable (x86_64) image; the VM lab below (scripts/test/lab) plays the multi-device scenarios.

Help page in a browser (scripts/test/ui-help.py)

python3 scripts/test/ui-help.py target/debug/varsto <screenshot dir> runs a throwaway vault and service in a temporary directory and drives the interface in Chromium (Playwright): the Help page with no vault, with a vault but no storage, with a storage and a folder, and locked, in English, Finnish and Swedish. It checks the first step, that the step buttons lead to the right form or dialog and that the "?" in the page header opens the page's guide, and saves screenshots.

VM lab (scripts/test/lab)

The step-by-step runbook is docs/testing/lab.md: host prerequisites, every lab.py command and scenarios.py option, the full run from nothing, results, cleanup and troubleshooting. A release needs every scenario, not only the ones for changed areas. This section is the summary.

Quick start:

python3 scripts/test/lab/lab.py up && python3 scripts/test/lab/lab.py build
python3 scripts/test/lab/lab.py services && python3 scripts/test/lab/lab.py install-bin
python3 scripts/test/lab/scenarios.py            # all scenarios; exit code = number that failed
python3 scripts/test/lab/lab.py services-stop && python3 scripts/test/lab/lab.py down

(The rendezvous scenarios also need a host build of varsto-rendezvous in <lab dir>/bin/; see the runbook.)

scripts/test/lab/lab.py up builds a small internet on one Linux host with libvirt: a WAN in a documentation range with an S3 server (rclone serve s3) and STUN, a home network behind a cone NAT router, an office network behind a symmetric NAT router, and a public device. lab.py build compiles a static binary in a build VM, install-bin puts it on every device, and scenarios.py plays 59 scenarios (SCENARIOS in scripts/test/lab/scenarios.py; scenarios.py --list prints them and --check is a self-check that needs no VM) against them, on storage format 3: setup and pairing (six words on both sides), sync and conflicts, selective sync, repair of damaged and missing packs, policies, Strongrooms, organizations and removal, revocation, the approval of joining devices (request, six words, approve, deny, viewer, a service that never approves), recovery escrow (recovery words, a lost owner replaced), removing a participant from a folder and a device from the vault, peer-to-peer on the LAN, through cone and symmetric NAT and during a slow upload, sharing, disk pools and the mailbox for an unplugged disk, no upgrade from the released alpha.15 (its vault is refused with a message to recreate it; a vault of the new format is refused by alpha.15; the way forward works), storage outage, a black-holed network, a crash during a push, clock skew, scale (20 000 files and 1 GiB, and many files in packs of every size class), garbage collection that waits for acknowledgements, a rolled-back ledger on a storage (the rollback warning), backups (restored on another device after an approval, a snapshot expired after the clock moves on), live activity, the bit-rot check, whole drives for disk pools (disk init, the fetch plan), restic, and forwarding (a selective device carries a phone's blocks from the phone to a storage) with the live board, pairing with a wrong address, and ledger loss (a device whose ledger directory was deleted restored from the bucket; the ledger lost from the bucket and both devices rebuilt by the service), torrents and YouTube channels through a spool directory (fake transmission and yt-dlp), and working offline (one of two storages black-holed during a sync and healed afterwards, a home LAN without internet that fetches from a peer of the saved directory, a pairing whose new device cannot reach the storage, a folder approval made offline and uploaded later), and the rendezvous service on the lab host (lab.py services starts <dir>/bin/varsto-rendezvous, a host build of -p varsto-rendezvous; every other scenario runs with VARSTO_RENDEZVOUS=off): both NATs observed, the symmetric NAT reached without a peer relay, the relay when the office router drops UDP, pairing across networks by code and by link (rv=, rvu=), and the server stopped. lab.py release builds the Linux, Windows and Android release packages in the build VM.

Lab logs

  • Every varsto run in the lab (CLI calls and the background service) gets VARSTO_LOG=debug. Set VARSTO_LOG on the host when running scenarios.py to use another level, e.g. VARSTO_LOG=trace scenarios.py --only sync.
  • After each scenario, passed or failed, scenarios.py copies the logs of every device VM to test-results/lab/logs/<scenario>/<vm>/, with paths relative to the home of user varsto: each Varsto home's logs/ (varsto-<component>.log and rotated varsto-<component>.N.log.zst, from the default ~/.local/share/varsto and the extra homes such as ~/share-home and ~/dl-home), service.log and the ~/*.log outputs of backgrounded commands. A failed scenario prints this path; results.json lists it under logs. Running a scenario again replaces its directory. Collection never fails a scenario; problems are printed as warnings.
  • The logs contain file and folder names from the generated test data, device names and storage endpoints, but never keys, passphrases or recovery words.
  • test-results/ is git-ignored, and CI does not upload these logs as artifacts.

Smoke suite (provision-vm.sh, run-suite.sh)

This part describes the smoke suite, which is separate from the VM lab. The smoke suite checks that the VM boots, accepts SSH, finished cloud-init, has a sane clock and has no route out of the test network.

Prerequisites

  • Linux with libvirt and QEMU/KVM (virsh, qemu-img, /dev/kvm), ssh, ssh-keygen, curl, sha512sum.
  • One of xorriso, genisoimage, mkisofs or cloud-localds to build the cloud-init seed.
  • Your user must be in the libvirt group; no root is needed. The scripts use qemu:///system and the storage pool default.
  • shellcheck if you change the scripts (shellcheck -x scripts/test/*.sh scripts/test/lib/common.sh).

What the scripts create and where

  • Base images are downloaded once from the distribution's official cloud-image site, verified against the published SHA-512 checksum, and cached in ~/.cache/varsto-test/images/ and in the libvirt pool.
  • Per-VM state (SSH key generated for that run, cloud-init files, generated XML) lives in ~/.cache/varsto-test/vms/<vm>/ and is removed by destroy-vm.sh.
  • Each VM gets a copy-on-write disk, a seed ISO and its own isolated libvirt network (no <forward>: no route to the LAN or the internet). All of these are named varsto-test-<distro>-<id>; the scripts refuse to touch anything else.
  • Results are written to test-results/<vm>/ (smoke.junit.xml, smoke.json, var-log.tar.gz); the directory is git-ignored.

Environment variables: VARSTO_LIBVIRT_URI, VARSTO_POOL, VARSTO_CACHE_DIR, VARSTO_RESULTS_DIR, VARSTO_VM_CPUS, VARSTO_VM_MEM_MIB, VARSTO_VM_DISK_SIZE, and VARSTO_KEEP_ON_FAIL=1 (keep a half-created VM for debugging when provisioning fails).

Exit codes

Code Meaning
0 Success; for run-suite.sh, the suite passed
1 The suite ran and at least one test failed
2 Usage error, unknown or not yet implemented distro or suite
3 Environment problem: missing tool, failed download or checksum, VM did not accept SSH

destroy-vm.sh exits 0 even if the VM is already gone. If provision-vm.sh fails it cleans up after itself.

Result format

smoke.json has the fields suite, vm, commit, result (pass or fail), started_utc, finished_utc and tests (a list of name, status, seconds, message). smoke.junit.xml is standard JUnit XML.

Other test tools

  • Interface tests in Chromium (Playwright; pip install playwright and playwright install chromium, or CHROMIUM=/path/to/chromium): scripts/test/ui-help.py, ui-no-reload.py (the page does not reload when the service restarts), viz-first-paint.py (the visualization page never draws invented content) and qr-scan-browser.py (QR scanner with a fake camera). Each takes a varsto binary and a work directory; read the header of the script for the exact arguments.
  • Page rules in plain Node: node scripts/test/import-ui.test.js and node scripts/test/viz-rules.test.js.
  • scripts/data/validate-providers.sh [--max-age-days N] [--fail-on-stale] validates data/providers/*.json against its schema and warns about stale prices.
  • Benchmarks and real-NAT tests on rented machines (scripts/bench, scripts/nat-test): docs/testing/benchmarks.md. They produce numbers, not pass or fail.
  • CI runs the Rust gates, the site-tool tests and the screenshot jobs on every pull request and push to main; what each job does is in BUILDING.md.

Results and reports

Use docs/testing/report-template.md. Automated and manual runs use the same fields so reports can be combined.

Release gates

  • Alpha to beta: all automated Linux suites green, and signed manual checklists for Windows, macOS, Android and iOS.
  • Beta to 1.0: independent security review published, reproducible builds verified.
