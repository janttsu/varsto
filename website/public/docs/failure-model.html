Failure model

From docs/failure-model.md in the repository, rendered 2026-10-14. These documents describe the main branch; the released version is 0.0.1-alpha.13. Sections marked 'after 0.0.1-alpha.13' are not in a release yet.

Design-stage model, written before the code. Much of it is now implemented as 0.0.1-alpha.13; the per-row notes and docs/spec/alpha-0-format.md record what is built. This document states what the design is meant to tolerate, what it limits, and what it does not cover. Statements such as "designed to" become claims about the product only after the tests named in TESTING.md show them.

Public statements about reliability must match this document. In particular, any marketing message about "no single point of failure" (requirement M-005) has to link here and must not claim more than this document lists.

Requirement IDs (F-, S-, P-, N-, M-) refer to the project requirements list. The wider design is described in docs/architecture.

Failure table

Failure Effect on data Effect on sync What prevents or limits it What does not Requirement IDs
Loss of all keys and of the recovery key Data in storage stays encrypted and cannot be read by anyone, including the project. There is no key escrow. No device can unlock or add new devices. A 24-word recovery key with checksum, shown once; optional threshold split kept in two or three physical places; a recovery test right after creation and then yearly. Users are told about the consequence before adding data. If every key and every recovery share are lost, nothing in the design can restore access. The recovery key is a single point of failure that the software cannot remove. Daily unlock is a passphrase; security keys for daily unlock are not built. S-002, S-014, F-042, S-005
Loss of one security key No data loss while another registered key or the recovery key is available. Unlocking continues with the remaining key. Strongroom folders stay locked until a registered key is present. Registering at least two keys for a Strongroom; a recovery kit for emergencies. Security keys unlock Strongroom folders only; the vault itself is unlocked with a passphrase, and keys for daily unlock are not built. Losing every key that wraps a Strongroom folder, together with the recovery key, leaves that folder unreadable. Whether a passphrase alone may unlock a normal vault is an open decision (TBD). S-004, S-005, S-012, S-014, F-042
A storage provider deletes data, rolls back to an older state, or locks the account Data survives if the configured policy keeps copies on another provider or on own devices. With one provider and no other copy, data can be lost. Sync continues through other storages and between devices. A rolled-back or missing object is meant to be detected through the ledger and flagged. Several providers (mirroring or erasure coding); own devices counted as copies; periodic scrub and repair from other copies; retention policies with alerts; the index and manifest are mirrored to every provider and to devices. A single provider with no second copy. A provider can still see object sizes and access times and can refuse service. Rollback detection is a design goal, not a tested property. F-017, F-018, F-020, F-021, F-031, F-032, S-006
Two devices stolen or destroyed together before changes reach cloud storage (use case UC-1) Changes that exist only on those two devices are lost. Earlier synced data is unaffected. Other devices do not receive the lost changes. The ledger knows which blocks exist only on certain devices; the app is meant to show "only on these devices, not yet in cloud" and policies can raise an alert as soon as a network is available. Devices in the same site count as one failure domain. Changes that did not leave the two devices cannot be recovered. A stolen, unlocked device can expose what that device could read. F-011, F-031, F-032, F-033, S-012
One device is stolen or lost Data on the device is encrypted at rest; other copies are unaffected. The device can be revoked from another device. Device revocation; a signed remote wipe command that is applied when the device next sees a network; Strongroom folders stay locked without the security key. Not built: rotation of storage credentials and folder keys on revocation, and automatic wipe after failed unlock attempts. Since 0.0.1-alpha.8: revocation cuts the device off from the ledger and from peers and gives the vault new keys for everything written afterwards, and the signed wipe order is applied when the device next reaches a storage (alpha-0-format.md section 21). Storage credentials are not rotated yet, so the revoked device can delete ciphertext until they are changed at the provider; automatic wipe after failed unlocks does not exist. A thief who keeps the device offline does not receive the wipe command. Revocation and encryption are the protection in that case, and wipe is an additional layer only. Wipe does not reach offline removable disks. F-035, S-001, S-009, S-011, S-012, F-033
Relay devices are down or blocked None. Peer discovery falls back in layers: known addresses, local network, the rendezvous record in the user's own storage, then manual invitation. Without a relay, some network types cannot connect directly and the app shows "not connected". Sync through shared storage is unaffected. No central tracker or account server; layered discovery: the LAN beacon, rendezvous records in your own storage and a relay through one of your own reachable devices (alpha-0-format.md section 15). There is no DHT (designed only, not built). Two devices behind restrictive NATs, with no shared storage and no reachable own device to relay, cannot find or reach each other outside the local network. A relay device sees IP addresses and traffic volume. F-012, F-013, F-005, N-001
Corruption or silent loss in one copy (bit rot, a peer that claims data it does not hold, a lost object) One copy is bad; other verified copies can repair it. Affected blocks are marked and fetched from other sources. Authenticated encryption and keyed hashes on every object; a periodic scrub re-reads the copies this device can read (alpha-0-format.md section 33, after 0.0.1-alpha.13, not in a release yet); self-describing packs so the index can be rebuilt. There is no proof-of-storage challenge: a peer's claim to hold data is not challenged. Corruption in every copy at the same time. Blocks that exist in only one place and have no verification yet. S-001, S-006, F-020, F-031, N-007
A disk of a disk pool is lost, stolen or dies The objects on it are lost unless another storage or disk holds them; the ledger and the pool index say which objects were only there (varsto disk retire prints the count). Stolen disks expose only ciphertext and a marker that names the pool and disk, not the vault. Sync is unaffected. Files whose only copy was on the disk stay pending and name the disk ("attach disk data-01 (shelf)"); policies count the disk's copies as verified at its last check and raise an alert when that ages out. Encryption of every object; the pool index and the disk's own index make the loss enumerable; durability policies that require a second copy elsewhere (another storage, or another disk group of the pool, alpha-0-format.md section 23); retiring a disk prints what exists only on it. Without a disk group rule (varsto disk group <pool> --copies N) or another storage, a lost disk is lost data. No SMART or health reading; no repair onto a replacement disk by itself. F-040, F-031, F-032, S-001
Removable disk not verified for a long time The disk may have degraded while offline. Its content is known only as of the last check. Sync is unaffected. The disk counts as a copy only while its claim has not expired. Claims in the ledger expire and become "assumed", not "present"; retention policies can require a check every few months and alert when it is overdue; on re-attach the disk is verified and damaged blocks are repaired from other copies; disk identity checks detect clones and restored disks. A disk that fails while it sits on a shelf. A disk with no second copy anywhere. Offline disks are protected only by encryption, not by wipe. F-040, F-031, F-032, F-033, S-001
Device clock is badly wrong No data loss is expected: event ordering uses logical clocks and sequence numbers, not wall-clock time. Ordering of changes is unaffected. Time-based items (claim expiry, freshness checks, alerts, request signing towards some providers) may be wrong or rejected on that device. Logical clocks and version vectors in the ledger; the VM lab plays scenarios with the clock ahead and behind (clock and clock_behind in scripts/test/lab/scenarios.py). A wrong clock can still cause false alerts or failed requests until it is corrected. Behaviour against real providers is not tested yet. F-031, F-003, N-007
A file is deleted by mistake, on any device None while the file is in the trash: its last version and its blocks are kept for the trash days (30 by default, per vault and per folder). The deletion syncs to every device like any change; each device that had the file also keeps a local trash copy. The vault-wide trash (after 0.0.1-alpha.13) lists deleted files on every device, and restores them from the storages (or the local copy) to their path or to name (restored), never overwriting; their blocks count as used for data moves, storage removal and fsck until they expire; an optional trash storage (for example a cold one) keeps them off warm storage, and reading them back from cold storage asks first (alpha-0-format.md section 43). A deletion noticed after the trash days, or one purged from the trash on purpose. Deletions made before the trash existed are only in the local trash copies. F-025
A file is overwritten by mistake (saved over, replaced by a sync from another device) None while a version of it is kept: the previous version and its blocks stay in the version history, thinned over time (every version for an hour, one per hour for a day, one per day for 30 days, one per week up to the history days, 90 by default, per vault and per folder or off). The new version syncs to every device like any change. The version history (after 0.0.1-alpha.13) lists a file's earlier versions on every device and restores one over the current file (which becomes a version itself) or under a new name, never overwriting without keeping; only changed blocks cost space; their blocks count as used like the trash's and can go to the trash storage; cold reads ask first (alpha-0-format.md section 50). A version the thinning let go (for example the 2 p.m. state of a file saved every minute, after more than an hour), anything past the history days, a folder with the history off, changes made between two scans or never uploaded. F-025
Malicious member of a shared folder The member can read what the folder shares and can change or delete files within the permissions given. Anything already downloaded stays with them. Their changes sync to other members like any other change. The trash keeps deleted files for the trash days, and a member's purges do not take entries out of the owner's trash (alpha-0-format.md section 43); the version history keeps what they overwrite, thinned over time (section 50); the change history view shows who did what; removing a member moves the folder to a new key (a share epoch) that only the remaining members receive, so new data is not readable by them (alpha-0-format.md section 24). Content the member already read or copied. Fine-grained permission rules are not specified yet (TBD). F-004, F-003, F-025, F-026, F-034, S-001
A storage loses its ledger objects, or a new storage is added None: every metadata storage and every full device holds the ledger. None: the next push of every device fills the storage again (its checkpoint and the batches after it). Each device lists from the newest own batch it last confirmed on each storage and starts over when that batch is gone (alpha-0-format.md sections 22 and 38). A storage that is the only one and loses everything while every device lost its ledger too (see the row on losing the ledger everywhere). F-017, F-020, N-007
A device's local ledger directory is deleted or damaged None expected; signing on would have reused sequence numbers (a fork) and fenced the device. The device signs nothing until it is restored: the service restores it at once; the command line stops and suggests varsto ledger rebuild. Detection when the engine opens (missing or unreadable heads, a pushed record above the head, a missing newest batch) and one short listing before every signature; the rebuild takes the device's own batches and checkpoint back from the storages, continues after the newest, and downloads the other devices' batches; unreadable files are set aside, never deleted (section 38). Events waiting in an unreadable pending.json (holdings and verifications of single fetches) are lost; a sync records the holdings again. F-020, F-031, N-007
A device is restored from an old backup, or two devices use one identity None from the restored copy; a second live copy of one identity can sign a history the other devices reject. The restored device is fenced (signs nothing) until it continues from its own later batches; the interface offers that with one button, the command line with varsto ledger rebuild. Two copies that published different batches are refused for good and the device must be paired again. Fencing on the first listing that shows this identity's newer batches; adoption only of batches signed by the device's key that chain onto what it holds; the refusal is remembered across restarts (section 38). A restored copy cannot be told from a live clone until the clone signs something the copy lacks: the copy may adopt and continue, and the clone is fenced at its next signature. S-001, F-031, N-007
The ledger is lost everywhere (every storage and every device), while keys, folder records, manifests and blocks remain Files are not lost: manifests and blocks are intact, and a device can still pull files. Where each block is, who wrote it and who verified it are lost until rebuilt. Policies, repair and verification see no copies until the rebuild; the service rebuilds automatically and notifies, the command line suggests varsto ledger rebuild --from-storage. The rebuild maps every stored object to its folder and block through the newest manifests and snapshots, verifies objects (all of a small vault, within a budget otherwise), claims them as this device's, and queues damaged ones for repair (section 38). Rebuilt claims are self-attested: "verified by another device" comes back only through later automatic verification. Other devices' backup snapshots are listed for restore only after their source device rebuilds. Cold storages are read only when confirmed. F-020, F-031, F-032, N-007
Two file names that differ only in case (or Unicode normalisation) reach a device whose filesystem ignores case (Windows, macOS, exFAT), or a name that filesystem does not allow (12:30.jpg on Windows) None: both files are kept. The second one is written under a local name with (2); a name Windows does not allow is written with look-alike private-use characters. Sync is unaffected: the device records its local names and maps them back, so no file looks renamed or deleted; the pull reports the renamed files. The per-folder local name map and the Windows mapping (alpha-0-format.md section 46). On that device the file shows under another name than on the others; which of the two gets the suffix depends on arrival order. A case-sensitive directory inside a case-insensitive folder, or a driver that silently changes names, is not detected. F-025
A synced folder's disk is not mounted, or its directory is emptied or replaced (an empty mount point, a wrong disk at the mount point) None: no file is read as deleted and nothing is downloaded into the wrong place. The folder is paused on this device until its marker .varsto-folder is back (or the user confirms the directory with varsto folder repair-marker); other folders and devices sync as usual. A marker naming the folder in every plain folder root; a missing or foreign marker pauses the folder with a notification and a banner (spec section 47). A directory whose marker is intact but whose files were removed some other way is handled by the mass-deletion guard below, not by the marker. Folders kept encrypted on a device and backup sources have no marker. F-025
Many files deleted at once, on this device or by another device (a script, a slip, a sync from a broken device) None until confirmed: deletions over the folder's threshold are held, nothing is published or deleted. After confirmation the files are in the devices' trash as with any deletion. The folder is paused on the device that holds the deletions until the user confirms or discards them; discarding restores the files from storage or republishes them as the newest version. Mass-deletion guard per folder (default: more than 50 % and more than 100 files, or more than 1000), the same check for another device's file list before files are moved to the trash (spec section 47). Deletions below the threshold sync at once (they are recoverable from the trash and history only). Deletions spread over several syncs are not added up. F-025
Software bug during the alpha stage Bugs can cause data loss or corruption. File formats and protocols may change without a migration path. The cryptography has not been independently audited. Devices may diverge or refuse to sync after a bug or an incompatible update. Prominent alpha warnings; version history; ledger invariants checked in deterministic simulation with fault injection; fuzzing and property tests; an index that can be rebuilt from the stored objects; the advice to keep independent backups. Bugs that tests do not find. Users who treat alpha software as their only copy. N-006, N-007, N-010, S-013, F-020
A storage reaches its quota (a bucket limit or a plan's size) No data loss: Varsto stops writing new blocks there before the quota (1 % kept free) and writes them to the folder's other storages. With no other storage that has room, new blocks stay only on the device that has them until there is room, so a policy can be at risk or violated meanwhile. Sync continues; uploads to the full storage wait. The status, the push report, the policy reasons and a notification name the storage ("storage X is at its quota (Y of Z)"). Vault-wide quotas published to every device; usage counted from the ledger plus an estimate of records, refreshed every sync and measurable on demand; a warning at 90 %. Usage is an estimate: devices writing at the same moment can pass the margin, and a provider's own limit is enforced by the provider, not by Varsto. F-017, F-020, F-032
A storage is drained (to switch providers) while the other storages lack room or the right places No copy leaves while it is needed: a block is dropped from the storage being drained only after the copies that stay (new ones read back and checked) still meet the folder's policy as far as it was met before, and never when it is the last copy. Blocks that cannot keep their policy elsewhere stay where they are. New blocks go to the other storages at once; the drain moves blocks in the background within a daily budget and reports what it waits for ("add another cloud storage or lower the policy", a quota). Records and ledger batches are copied to the other storages before the storage is marked drained. Policy check per block before every drop; drops sealed in the ledger before deletion; resumable runs; quotas respected on the receiving storages; cold reads only after confirmation. A drain that cannot finish keeps the storage (and its bill). A device that has not synced since the drain started can still write a block there until it does; the drain then moves it. F-017, F-018, F-032, F-043
The maintainer disappears Existing data remains readable by anyone holding the keys: the storage format is documented; a standalone reader tool does not exist yet (docs/spec/format-versions.md). Sync keeps working between installed clients, because there is no project-run server to switch off. Open, documented storage format and protocols; source-available code; no account server; restic-compatible backup option; recovery kit independent of the application. Bug fixes, security updates, store releases and OS compatibility stop. Continued development by others is limited by the licence terms. Clients may stop working after operating system changes. F-005, F-019, F-020, N-004, F-042

Remaining single points of failure

The design reduces single points of failure but does not remove these:

  • The user's keys and recovery kit. There is no escrow and no account recovery. This is deliberate (S-014).
  • The user's own site and provider configuration. The software cannot verify geography. A provider region name does not prove where a data centre is, and two "different" providers can share infrastructure (F-033).
  • The software itself. One code base implements the ledger, the cryptography and the sync. A bug there can affect every copy. Independent implementations of the readers and an independent audit are goals, not facts (N-004, S-007).
  • The release pipeline and the maintainer. Updates and signed releases depend on a small team (S-007, N-005).
  • Platform dependencies. Operating system keystores, hardware security keys and mobile background limits are outside the project's control (S-005, F-036).
  • Optional infrastructure. Relays and DHT bootstrap nodes are not required for sync through shared storage, but without them some networks cannot connect directly (F-012, F-013).
